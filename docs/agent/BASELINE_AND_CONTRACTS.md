1. `ZEUS_ARCHITECTURE.md` starts with an **obsolete-draft warning** and points to `../docs/full_spec/README.md`; that spec path is not in the remote HSO root. The draft contains explicitly invalid runtime claims and must not be used as current architecture.
2. The root README discusses 6-character pairing and a generic 34-field control; `PRODUCT.md` currently defines **8-character hexadecimal pairing**, and `config-schema.ts` describes **34 stored keys for v13/v14 and 37 for v15**. Verify source for the specific path/version, and ask the operator to resolve behavior changes.
3. The README suggests automatic mock fallback without env, while `src/lib/supabase.ts` explicitly throws if NEXT_PUBLIC keys are absent. Check the actual `services/api.ts` selection and runtime before stating an env-free preview works.
4. `PRODUCT.md` prohibits changes to database schema/migrations and `ZeusApi` interface for this product scope. Treat these as locked until explicitly reprioritized; do not construe “build a feature” as authorization to migrate cloud state.
5. `skills-lock.json` records external UI skill pointers, **not proof they are installed in the active agent runtime**. Existing UI guidance remains, but run-and-report only verifiable checks.

- `DeviceStatus` UI three states: online/offline/error. `HealthStatus`: running/degraded/stopped derived from process+snapshot/CTL, not combat flags.
- Queue accepted/DB saved != Agent applied/command completed. Show the highest **observed** state only.
- Real map 0 is valid; no-spot wire tuple `(0,-1,-1,-1)`; `__none__` is presentation only.
- Privileged database changes and deployment are separate human-controlled gates.
